# Reptr product audit

Audit date: 5 November 2026. Method: read every route, shared component, schema and seed script, then drove the app in Chromium at phone size (390 × 844) and desktop size against a local database.

**Verdict:** the backend is sound, and the workflows mostly work when the app is opened at `http://localhost`. The product problem is breadth without hierarchy. There are 22 screens, 6 nav tabs and dozens of metrics, so the five things people do every day (start a workout, log sets, log weight, check progress, see the week) compete with everything else.

Severity: **Critical** means a core workflow is broken or data is wrong. **High** means a core workflow is confusing or hidden. **Medium** means a secondary screen is cluttered or inconsistent. **Low** means polish.

## Data and backend

- Ownership: every module query filters by `user_id`, and the tables have RLS policies with tests. See F6.
- Workouts: snapshots are saved idempotently with a version, and two-device edits are merged. Sets survive refresh (IndexedDB). This is OK.
- Routines: saved in a transaction, with items replaced on save. Workouts copy exercises at start, so editing a routine never changes past workouts. This is OK.
- Offline: quick logs are queued with idempotent op ids. This is OK.
- Timezone: day boundaries use the user's timezone cookie. This is OK.
- Units: stored in kg and cm, converted for display. Imperial entry needs a check on every form.

## Testing gaps

The existing E2E suite covers 6 journeys. Missing: a fresh user with no demo data, a weight log/edit/delete cycle, a routine reopened and then started, a calendar day detail, an offline workout replay, two-user isolation in the browser, and the 127.0.0.1 origin.
